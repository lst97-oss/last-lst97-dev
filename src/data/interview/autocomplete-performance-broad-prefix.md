# How would you improve autocomplete performance when a prefix matches a very large number of addresses?

- **Category:** Applied Project Questions
- **Source ID:** autocomplete-performance-broad-prefix
- **URL:** https://www.lst97.dev/chat

My database optimisation experience is still developing, so some of the original optimisation work on this project was developed with AI assistance. However, I validated the implementation myself through performance testing and by randomly selecting addresses from the source dataset to make sure different address formats could still be retrieved correctly. For a very broad prefix, I would avoid returning or ranking every matching address. Instead, I would first limit the number of candidates returned and use the more specific information available in the query, such as postcode, suburb, street and street number, to progressively narrow the search space. I would also make sure the commonly searched fields have appropriate indexes and inspect the PostgreSQL query plan using tools such as EXPLAIN ANALYZE to check whether the indexes are actually being used. On the API side, I would return only a small number of highly ranked suggestions, such as the top 10 or 20 results. On the frontend, I would also debounce requests so that we are not querying the server for every individual keystroke. If this became a high-concurrency production service, I would benchmark the existing PostgreSQL approach first and then consider additional techniques such as caching frequently requested prefixes or introducing a dedicated search engine if PostgreSQL became the bottleneck.
