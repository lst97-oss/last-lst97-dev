# How would you scale address autocomplete from thousands to millions of requests per day?

- **Category:** System Design and Architecture
- **Source ID:** scaling-autocomplete
- **URL:** https://www.lst97.dev/chat

I haven't personally operated a system at millions of requests per day yet, so I would approach this incrementally rather than immediately introducing a complex distributed architecture. The first thing I would do is understand the expected traffic pattern, peak request rate, latency requirement and acceptable availability. If the application only has a relatively small number of users, I would avoid unnecessary microservices and focus first on having a well-indexed database, rate limiting, a reverse proxy, caching, monitoring and appropriate DDoS protection. For address autocomplete specifically, I would also look at caching frequently requested prefixes because many users are likely to search for similar suburbs, streets and postcodes. I would benchmark the database queries and optimise indexes before adding infrastructure. If traffic continued to increase, I would make the API stateless so that multiple application instances could run behind a load balancer and scale horizontally. For background workloads that are not part of the critical autocomplete path, such as email delivery, PDF generation or other asynchronous processing, I would separate them into workers or services connected through a queue. This allows those workloads to scale independently without affecting search latency. For the database, I would avoid premature sharding because distributed databases introduce significant operational complexity. I would first use techniques such as connection pooling, query optimisation, caching, vertical scaling, high availability and potentially read replicas. Only if the database itself became a proven bottleneck would I consider partitioning or sharding the data. The main principle would be to measure where the bottleneck actually is and scale that component rather than redesigning the whole system prematurely.
