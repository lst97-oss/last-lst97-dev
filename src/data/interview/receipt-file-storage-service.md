# How would you design the file-storage service used for receipt uploads?

- **Category:** System Design and Architecture
- **Source ID:** receipt-file-storage-service
- **URL:** https://www.lst97.dev/chat

For receipt uploads, I would generally store the files in object storage such as Cloudflare R2, which provides an S3-compatible API, rather than storing the binary data directly in the application database. I would separate the upload process into temporary and permanent states. When a user starts an upload, the file would initially be marked as pending. The database would store metadata such as the object key, original filename, MIME type, size, owner, upload status and timestamps. Once the user saves the expense or receipt successfully, the application would mark the file as attached or completed. A scheduled cleanup job could periodically find uploads that have remained pending beyond a defined time limit and remove both the object and its metadata. This prevents abandoned uploads from accumulating indefinitely. For validation, I would check the maximum file size, permitted extensions and detected file type. I would not rely only on the MIME type supplied by the browser because that can be spoofed. For stronger content-type detection, a tool such as Google's Magika could inspect the actual file contents and determine whether the uploaded data matches the expected file type. For permissions, authentication and authorisation should be checked by the application. Users should only be able to access receipts belonging to resources they are authorised to view. I would normally keep the storage bucket private and provide access through the application or short-lived signed URLs rather than exposing permanent public object URLs. I would also design the workflow so that failures are recoverable. For example, if the database transaction succeeds but the storage operation fails, or vice versa, the system should record enough state for a cleanup or retry process to reconcile the inconsistency.
