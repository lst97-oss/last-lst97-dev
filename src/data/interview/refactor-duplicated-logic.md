# You have an existing project with duplicated logic and poor structure. How would you refactor it without breaking users?

- **Category:** System Design and Architecture
- **Source ID:** refactor-duplicated-logic
- **URL:** https://www.lst97.dev/chat

Before changing the implementation, I would first establish tests around the existing behaviour. Even if the existing architecture is poor, those tests give us a behavioural baseline and help make sure that refactoring does not accidentally change what users currently depend on. I would then refactor incrementally rather than rewriting the entire system at once. If many callers depend on the existing interface, I could introduce an adapter or facade that keeps the same public API while moving the internal implementation toward the new structure. This lets us improve the internals without forcing every caller to change at the same time. For duplicated business logic, I would identify the actual shared domain behaviour and move that into an appropriate reusable module or service rather than simply creating generic helper functions everywhere. After each change, I would run unit tests, integration tests and relevant end-to-end tests to confirm that the observable behaviour remains the same. If the application supported feature flags or controlled rollout, I could also gradually switch traffic from the old implementation to the new one and monitor for regressions before completely removing the old code. Most of my projects so far have been developed from the ground up, so I have had more experience preventing structural problems than performing large refactors of mature legacy systems. I try to achieve that through clear separation of concerns, modular architecture and automated testing. However, if I inherited an existing system, my priority would be to understand and preserve its behaviour first, then improve the architecture incrementally rather than immediately rewriting it.
