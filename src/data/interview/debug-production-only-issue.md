# How would you debug a production-only issue that cannot be reproduced locally?

- **Category:** System Design and Architecture
- **Source ID:** debug-production-only-issue
- **URL:** https://www.lst97.dev/chat

For a production-only issue, good observability is essential because attaching a debugger directly to production is usually not the first option. I would start by identifying the affected request, user action or time window. If the system uses correlation or request IDs, I would use that ID to trace the request across the application logs and any downstream services. I would inspect the request parameters, application logs, exceptions, database operations and external-service responses to determine where the actual behaviour diverged from what we expected. I would also compare the production environment with local or staging environments. Production-only bugs can come from configuration differences, environment variables, dependency versions, data characteristics, concurrency, caching or infrastructure behaviour rather than only from application logic. Once I narrow down the conditions, I would try to reproduce those conditions in a controlled environment using sanitised or representative production-like data. If necessary, I would add targeted structured logging or tracing around the suspected path and deploy that instrumentation rather than making speculative changes directly in production. I have encountered an example where a problem appeared only in the deployed Next.js environment because of a framework-version issue. After isolating the version as the difference, downgrading to the known-working release resolved the production problem. That experience reinforced for me that production debugging should include both our own application code and differences in the runtime, dependencies and infrastructure.
