# What would you monitor in a production web application, and how would each metric help you diagnose an incident?

- **Category:** System Design and Architecture
- **Source ID:** production-monitoring-metrics
- **URL:** https://www.lst97.dev/chat

I would monitor both technical health and user-facing behaviour, but I would treat them as two different categories. For technical monitoring, I would start with error rate, request latency, request volume and resource saturation such as CPU, memory and database connections. Error rate tells me whether requests are failing. Latency helps identify performance degradation even when requests are still technically succeeding. Traffic helps determine whether an incident corresponds with an unusual increase in load, and resource metrics can show whether the application, database or infrastructure is approaching capacity. For the database, I would monitor slow queries, connection-pool usage and query latency. For background workers, I would monitor queue depth, processing time and failed jobs because a growing queue can indicate that workers cannot keep up even though the web application still appears healthy. I would also use structured logs, request IDs and ideally distributed tracing so that an individual failed request can be followed across the API, database and external services. On the frontend, I would monitor JavaScript errors, failed API requests and performance metrics. For product analytics, I have used PostHog. Session recordings and event tracking can be useful for understanding the sequence of actions that caused a problem. Heatmaps and interaction analytics can also help identify usability problems, such as users repeatedly failing to discover an important control. I would therefore use observability tools to answer two different questions: technical monitoring tells me whether the system is healthy, while product analytics helps explain how users are actually interacting with it.
