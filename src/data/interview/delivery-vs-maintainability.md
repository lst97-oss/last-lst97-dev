# How would you balance fast delivery against maintainability when deadlines are tight?

- **Category:** System Design and Architecture
- **Source ID:** delivery-vs-maintainability
- **URL:** https://www.lst97.dev/chat

I don't think the correct answer is always to prioritise maintainability over delivery. In a real project, the goal is to protect the parts of the system where poor quality would create unacceptable risk while reducing scope or complexity elsewhere. Before implementation, I would first clarify which requirements are actually necessary for the deadline and which features can be postponed. For a tight schedule, I would prefer established technologies and libraries that the team already understands rather than introducing an unfamiliar framework simply because it may look technically better. I would still protect the fundamentals: clear separation of concerns, readable code, validation, security and automated tests around critical business behaviour. However, I would not try to create the perfect abstraction or architecture for every feature. If a simpler implementation is sufficient and can be safely changed later, I would choose that instead of over-engineering the first version. Where compromises are necessary, I would make them explicit and record the technical debt rather than allowing temporary shortcuts to become undocumented permanent architecture. I also try to structure the application so that individual components and business domains are reasonably isolated. That makes it easier to improve or replace an implementation after release without affecting unrelated parts of the application. So for me, balancing delivery and maintainability means reducing scope before reducing correctness, keeping critical paths well tested, avoiding unnecessary abstraction, and deliberately managing any technical debt created by the deadline.
