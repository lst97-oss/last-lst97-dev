# Local data model, availability search and availability watchers

- **Category:** Booking and Notifications
- **Source ID:** smartplay-search-and-watchers
- **URL:** https://www.lst97.dev/projects/smartplay-hk-oss
- **Visibility:** Public

I validate every external response with Zod at the boundary and normalise it into District, Facility, FacilityType, Session and CrawlJob entities, because SmartPLAY's own nested structure — morning/afternoon/evening periods, districts, venues, sessions and metadata — is not the structure I want to expose through the rest of the application. Zod at the boundary stops an invalid upstream response from silently corrupting internal state, and once data enters the core application the frontend never needs to understand SmartPLAY's original response format. That separation is what let the UI and the crawler evolve independently.

Sessions carry a composite uniqueness constraint on their business identity: venue plus facility plus date plus start time equals one session. Availability crawling repeatedly sees the same sessions, so creating a row per crawl would produce duplicates; instead the stable row is updated as availability changes. I enforce this in the database rather than in application code, because the persistence layer is where concurrent operations cannot accidentally bypass it. The schema also carries indexes built around the real access patterns — venue + date, date + available, date + facility, and available + verification time — so the model is designed around the expected query workload rather than indexing after performance degrades. On top of that sits an aggregated `AvailabilityStats` representation across date, district, centre and facility, holding total sessions and available sessions, batch-written with PostgreSQL operations where appropriate, so the UI shows availability counts without recomputing every raw row on each page request.

The booking filter chain narrows collected sessions by date, district, centre, facility type, venue, search text and availability state, and that state is reflected in the application navigation rather than living as temporary component state, which makes views navigable, revisitable and shareable. Watchers complete the loop: a watcher records venue, facility, date, start time and end time; the watch evaluator compares observed availability state after a crawler refresh and emits a WatchHit only on change; the notification service — deliberately separate from watcher evaluation — then delivers in generic webhook, Discord or Slack format, recording notification outcomes so delivery failures are observable rather than silently discarded. Ownership comes from anonymous browser sessions rather than accounts, with ownership checks preventing one session modifying another's watchers, and Cloudflare Turnstile protects watcher creation because it is server-side work that creates persistent rows and future notification traffic.
