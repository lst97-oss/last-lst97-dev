# HTTP API, access control and measured performance

- **Category:** API and Operations
- **Source ID:** gnaf-api-and-operations
- **URL:** https://www.lst97.dev/projects/gnaf-address-autocomplete
- **Visibility:** Public

The service is a small HTTP API served by Bun and Elysia, exposing `GET /suggest`, `GET /address/:id`, `GET /healthz`, `GET /readyz`, `GET /openapi.json` and `GET /api/stats`, with the full contract published as OpenAPI 3.1 alongside generated API documentation. A suggestion request is conceptually `GET /suggest?q=12+main+st+sydney` with an `X-API-Key` header, and each returned suggestion carries the display string plus `locality`, `state`, `postcode`, `lat` and `lon` — for example `12 MAIN ST, SYDNEY NSW 2000` at `-33.8618`, `151.2083`. I kept this surface deliberately narrow so the search engine stays independent of whichever client consumes it; the backend has no dependency on the frontend being React, mobile or something else, and `/address/:id` serves detailed lookup by G-NAF identifier.

Because autocomplete is called continuously while a user types, an open public endpoint generates significant traffic, so the project ships its own API-key system. Keys can be bound to authorised domains and are stored as cryptographic hashes rather than raw tokens. Controls include per-key rate limiting, API-key generation limits, domain verification, allowed origins, key expiry and Cloudflare Turnstile during key registration. Since the keys carry high-entropy random values, I use a fast cryptographic hash on the verification path instead of a password-oriented slow KDF — a password has low user-generated entropy and benefits from Argon2 or bcrypt, but adding that cost to every autocomplete request would only inflate latency. That was choosing the primitive from the actual threat model rather than applying one everywhere. On the caching side there is a bounded in-process LRU cache with a configurable TTL, because a user typing `m`, `ma`, `mai`, `main`, `main s`, `main st` repeats earlier queries; a distributed cache was deliberately skipped because the current deployment does not need one.

For observability I split liveness from readiness: `/readyz` validates dependencies such as the database and search dataset before reporting the service ready for traffic, rather than merely reporting that the process started.

The performance target was p95 < 50 ms for uncached autocomplete. A benchmark of 1,000 mixed query shapes against the complete dataset measured, in my development environment, p50 ~7 ms, p95 ~26 ms, p99 ~28 ms, an average of ~10 ms, and a repeated cached query under 1 ms. The application-level suggestion cache was disabled for that run so the numbers represented the search path rather than cache hits, and the environment was an M5 Pro MacBook Pro with PostgreSQL running through Docker — these are measurements from that environment, not universal infrastructure guarantees.

Deployment is container-based. Cloudflare fronts a Cloudflare Tunnel into the G-NAF API container, which talks to a PostgreSQL container on the internal Docker network backed by a persistent volume, so the database is never exposed directly to the public internet. Images are built and published through GitHub Actions CI/CD, and health checks let the deployment environment verify that the API and database are actually available.
