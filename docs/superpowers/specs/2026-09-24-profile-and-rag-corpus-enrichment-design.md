## Repository-document enrichment

Refresh every owned-repository and third-party-contribution Markdown document using the existing local repository inspection flow. Each report should begin with a compact retrieval-oriented summary and preserve the evidence-based sections already produced by `github-summary-markdown.ts`:

- canonical repository name, owner, visibility, and contribution relationship;
- concise purpose/problem summary and product/domain synonyms useful for natural-language queries;
- observed features and the technology/framework stack;
- tracked-file counts and evidence-backed architecture/design patterns;
- third-party contribution kind/count and available contribution references;
- code paths supporting claims, with inferred claims explicitly labeled;
- limitations when source inspection or contribution data is incomplete.

Repository-purpose facts may come from inspected code, manifests, tests, and safe project documentation, or from explicit owner-provided context. Do not invent features when source inspection is unavailable. In particular, the owner-provided description may establish that SplitTab is an expense-management app, but technical stack or implementation details still require repository evidence. Do not duplicate the full biography into every repository document; use concise identity/ownership context and retrieval terms instead.

## Security and visibility

- Keep all repository cloning and code inspection local; do not send private repository code or Markdown to hosted model providers.
- Apply the existing secret/content safety checks to generated Markdown before writing or indexing.
- Keep private owned/contribution documents under their existing `private` paths and index them with `is_public=false`; public chat retrieval must continue filtering to `is_public=true`.
- Never copy credentials, secret values, private keys, local configuration, or sensitive personal data into Markdown. The profile's name, codename explanation, education, work history, skills, and supplied public project references are intentionally owner-provided profile facts.
- Do not alter frontend project-card behavior or publish/stage private summaries as part of the corpus refresh.

## Failure and verification behavior

- Preserve last-known-good Markdown and vector chunks if a repository clone, code inspection, secret scan, embedding, or database write fails; report the affected source and sanitized failure category.
- Do not perform stale-source deletion from an incomplete GitHub inventory.
- Verify all 134 Markdown paths are accounted for after refresh, and reconcile generated file identities against indexed source IDs and chunk counts.
- Verify profile retrieval for queries such as “What does LST97 mean?”, “What is Nelson's background?”, and “What does Nelson do outside software development?”. Verify representative public repository and contribution queries, and prove private documents remain excluded from public search.
- Run focused tests, the full `bun test` suite, `bun run typecheck`, and `git diff --check`; report any database-backed tests not run because of environment constraints.
